4. CORRECCIÓN Y FUNCIONAMIENTO DE DESCARGA DE BACKUPS (.DB)
================================================================================

• ¿Por qué salía el error "File wasn't available on the site try to sign in on the site then download again"?
  - Causa técnica: Los navegadores web (Chrome, Edge, Safari), al hacer clic en un enlace
    de descarga directa tradicional, no envían cabeceras personalizadas de JavaScript
    (Authorization: Bearer <token>). El servidor devolvía un código HTTP 401 (No autorizado),
    y Chrome lo traducía como "El archivo no está disponible en el sitio, inicia sesión y descarga de nuevo".
  - Solución aplicada:
    1. Se actualizó el middleware de autenticación del backend (authMiddleware.js) para
       aceptar el token firmado JWT tanto por cabecera Bearer como por parámetro seguro (?token=...).
    2. En el modal del Frontend (BackupsModal.jsx), el botón de descarga inyecta automáticamente
       el token del usuario autenticado en la URL de descarga:
       /api/admin/backups/:filename?token=<TOKEN_JWT>
    3. Desplegado en la revisión 00005-66k de Google Cloud Run. Ahora al dar clic en
       "Descargar .db", el archivo se descarga inmediatamente sin ningún error.

8. POLÍTICA DE BACKUPS: ¿EN TABLA O ARCHIVOS? ¿AUTOMÁTICOS O MANUALES?
================================================================================

¿Cómo se almacenan los backups de la base de datos?
- NO se guardan dentro de la misma tabla de datos operativos, porque si el archivo de la
  base de datos sufriera una corrupción de disco, se perderían simultáneamente los datos
  y los respaldos.
- Por estándar de ingeniería, U-Pad implementa almacenamiento dual:
  1. Archivo Snapshot Físico: Cada backup se genera mediante SQLite VACUUM INTO como
     un archivo consistente en caliente (.db) independiente en:
     backups/upad_relational_backup_<TIMESTAMP>.db
  2. Tabla Catálogo de Auditoría: Se registra en la tabla "backups_history" de la BD:
     - id (identificador único del backup)
     - filename (nombre del archivo generado)
     - file_path (ruta física)
     - size_bytes y size_formatted (peso en KB/MB)
     - tipo: 'AUTOMATICO' o 'MANUAL'
     - creado_por (correo del developer o sistema)
     - creado_en (marca de tiempo ISO)

¿Los backups son automáticos o manuales?
- SON AMBOS (Cubre 100% el requerimiento):
  * Automáticos: El backend (server.js) tiene programado un temporizador automático
    que ejecuta un backup periódico cada 12 horas y una comprobación en el arranque inicial.
  * Manuales: El desarrollador mantiene el botón "Backups [Dev]" en la cabecera web
    para generar copias instantáneas a demanda y descargarlas con el botón "Descargar .db".

¿CÓMO SE DEFINE LA CANTIDAD DE USUARIOS Y EL TIEMPO EN EL COMANDO K6?
--------------------------------------------------------------------------------
Los parámetros se introducen directamente mediante banderas (flags) en la línea de comandos:

  • --vus <CANTIDAD>       : Define los Virtual Users (usuarios concurrentes simulados).
                             Ejemplo: --vus 7500   o   --vus 1500   o   --vus 250
  • --duration <TIEMPO>    : Define la duración de la prueba (s = segundos, m = minutos).
                             Ejemplo: --duration 5s   o   --duration 10s   o   --duration 1m
  • --iterations <CANTIDAD>: Define el número exacto de peticiones totales a repartir.
                             Ejemplo: --iterations 10000
